# RAG V0.3 Handoff

## Repository state

- V0.2 released baseline: `21046beadd99233ff0a234cba441f0ed1823e387`
- Development branch: `feat/v0.3-langchain-integration`
- This handoff was prepared before the V0.3 release commit and push.

## Implemented

- Optional `langchain-core` dependency for Python 3.10+.
- `search_knowledge_base` as a `StructuredTool` over the unchanged
  `RAGService.retrieve()` method.
- Structured, allowlisted source output with TXT common metadata and CSV/PDF/PPTX locators.
- Safe no-evidence and retrieval-error states.
- A two-message `ChatPromptTemplate` that keeps retrieved content out of the
  System Message and preserves the V0.2 grounding/injection rules.
- A typed Runnable / LCEL path that bridges to the existing `LLMClient.complete()`.
- No-evidence short circuit, bounded context, exact source list, empty-answer
  fallback, and safe exception handling.
- Local Mock compatibility for both DashScope and OpenAI-compatible adapters.

## Explicit non-features

- No LangGraph.
- No Agent or automatic tool loop.
- No FastAPI.
- No provider-native `tools` request or `tool_calls` response parsing.
- No `bind_tools()` support in `LLMClient`.
- No V0.2 RAG/index/provider rewrite.
- No real OpenLux or DashScope call in V0.3.

The correct capability description is **LangChain Tool + Runnable**, not real
Tool Calling.

## Suggested V0.4 direction

Use the stable Pydantic Tool input/output models as LangGraph state boundaries.
Add a small, explicit provider chat/tool-calling protocol only if a target API's
schema and account capability have been confirmed. Validate tool arguments,
limit tool iterations, preserve the no-evidence short circuit, and keep all real
provider tests opt-in and excluded from CI. Do not replace LlamaIndex retrieval.
