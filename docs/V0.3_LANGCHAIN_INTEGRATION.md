# RAG V0.3 LangChain Integration

## Scope and status

- V0.2 baseline: `21046beadd99233ff0a234cba441f0ed1823e387`
- Development branch: `feat/v0.3-langchain-integration`
- Classification: **LangChain Tool + Runnable**
- Real model Tool Calling: **not implemented**
- Real LLM calls made during V0.3 development: **0**

Acceptance environment: Ubuntu 22.04, Python 3.10.12,
`llama-index-core 0.14.25`, `langchain-core 1.7.0`, Pydantic 2.14.1, and
HTTPX 0.28.1.

V0.3 adds an optional orchestration layer. It does not replace the tested
LlamaIndex parsing, splitting, Embedding, vector index, persistence, retrieval,
metadata, or provider adapters.

## Responsibilities

| Layer | Responsibility |
|---|---|
| LlamaIndex | `Document`, `SentenceSplitter`, `VectorStoreIndex`, persistence, reload, Top-K retrieval and similarity scores |
| Existing project services | multi-format loading, cleaning, metadata contract, `RAGService.retrieve()`, and `LLMClient.complete()` providers |
| LangChain Core | structured retrieval Tool, chat prompt messages, Runnable composition, and output parsing |

The LangChain module receives an already initialized `RAGService`. It never
creates an Embedding model, rebuilds an index, reloads source files, or owns a
second vector store.

## Tool definition

`create_search_knowledge_base_tool()` returns a `StructuredTool` named
`search_knowledge_base`. Its generated input Schema has one required field:

```json
{
  "type": "object",
  "required": ["query"],
  "properties": {
    "query": {"type": "string", "minLength": 1, "maxLength": 4096}
  }
}
```

Whitespace-only input is rejected by Pydantic validation. `top_k` and
`min_similarity` are fixed when the Tool is constructed so a model cannot
silently weaken retrieval policy. The tool calls only `RAGService.retrieve()`.

The output is a serializable dictionary:

```text
status: ok | no_evidence | error
message: safe public status
results:
  - source_number
  - text
  - score
  - source_label
  - metadata:
      source_file
      file_type
      source_id
      chunk_index
      page_number | slide_number | row_number
```

Only allowlisted metadata is exposed. Internal exceptions and paths are not
returned to the model. Tool descriptions and status messages explicitly mark
retrieved content as untrusted data. This contract can be passed directly
through a future LangGraph tool node without changing the existing search API.

## Prompt design

`DOCUMENT_QA_PROMPT` is a `ChatPromptTemplate` with two messages:

1. A fixed System Message defines grounding, exact no-evidence fallback,
   citation rules, and indirect prompt-injection restrictions.
2. A Human Message contains the retrieved context and user question inside
   structural tags.

No document text is interpolated into the System Message. Angle brackets in
the question, source labels, and retrieved chunks are converted to full-width
characters before formatting, preserving the V0.2 delimiter defense. Document
instructions therefore remain untrusted content and are never promoted to
system authority.

## Runnable / LCEL flow

`create_langchain_rag_chain()` returns a real LangChain Runnable with typed input
and output contracts:

```text
{question}
  → StructuredTool.invoke({query})
  → no-evidence/error decision
  → bounded numbered context
  → ChatPromptTemplate
  → RunnableLambda(existing LLMClient.complete)
  → StrOutputParser
  → {answer, sources}
```

No-evidence results return the existing fixed fallback before the generation
chain, so the LLM call count remains zero. The output source list contains only
the exact, ordered fragments included in the bounded prompt. An empty LLM answer
uses the same fallback. Unknown provider exceptions are wrapped in a public
message; the existing provider adapters retain their more specific safe errors.

## Data and metadata contract

The adapter consumes the unchanged `SearchResult` fields:

```text
text: retrieved chunk text
score: cosine similarity or None
metadata:
  required: source_file, file_type, source_id, chunk_index
  optional locator: page_number, slide_number, row_number
```

Source numbers start at 1 and remain aligned across tool output, prompt blocks,
and Runnable output. Missing or invalid required metadata produces a safe tool
error rather than a partially traceable result.

do not load BGE, read `.env`, or send network requests. Coverage includes:

## Real API and Tool Calling status

No OpenLux or DashScope request was made in V0.3. V0.2's real OpenLux evidence
remains historical validation of text completion, not Tool Calling.

The current `LLMClient.complete(prompt: str) -> str` contract sends plain text.
It does not expose LangChain chat-model methods such as `bind_tools()`, and the
OpenAI-compatible adapter does not send a `tools` array or parse `tool_calls`.
`StructuredTool` therefore supplies a testable schema and callable application
component, but the model does not autonomously choose the tool. Claiming Agent
or real Tool Calling support would be inaccurate.

## Failure behavior

| Failure | Behavior |
|---|---|
| blank question | validation error before retrieval |
| no result after threshold | fixed no-evidence answer; LLM not called |
| retrieval/internal metadata error | safe `知识库检索暂时不可用。` status/error |
| empty LLM answer | fixed no-evidence answer with the supplied source list |
| existing provider `RAGError` | safe provider message preserved |
| unknown LLM exception | wrapped as `LLM 生成失败，请稍后重试。` |
| context limit reached | stop adding chunks; return only sources actually sent |

## Known limitations

- No CLI command currently exposes the optional LangChain path; it is a Python API.
- No asynchronous or streaming adapter is implemented.
- Tool output is structured in Python, but no LLM-native Tool Calling protocol is implemented.
- Citation syntax is requested and source mapping is preserved, but generated claims are not automatically fact-checked.
- Prompt-only injection defenses reduce risk but cannot guarantee resistance to every indirect attack.
- LangChain Core brings its declared transitive packages, including the LangSmith client; no LangSmith tracing endpoint, key, or network call is configured.

## V0.4 LangGraph reuse

A future LangGraph branch can use `SearchKnowledgeBaseInput` as tool-node input,
`SearchKnowledgeBaseOutput` as state evidence, and `LangChainRAGOutput` as the
terminal response contract. Keep retrieval policy (`top_k`, threshold, context
limit) outside model-controlled arguments. Before calling this real Tool
Calling, add an explicit chat-model adapter that sends provider `tools` schemas,
validates returned arguments, parses `tool_calls`, enforces a bounded loop, and
is tested separately with opt-in paid requests. The existing LlamaIndex pipeline
should remain the retrieval backend.
