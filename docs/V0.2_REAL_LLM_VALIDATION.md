## Method

The validation script creates four non-sensitive synthetic Chinese documents:

- `project_overview.txt`: project support channel;
- `service_catalog.csv`: one document per service row;
- `release_policy.pdf`: one document per text-layer PDF page;
- `release_training.pptx`: one document per slide, including an indirect prompt
  injection sample clearly marked as untrusted data.

It then uses the existing project components in this order:

```text
MultiFormatDocumentLoader
→ clean_documents
→ SentenceSplitter
→ BAAI/bge-small-zh-v1.5
→ VectorStoreIndex persistence
→ PersistentRAGIndex.load
→ Top-K retrieval and score filtering
→ RAGService
→ configured LLM client (only after explicit paid-call confirmation)
```

The default script mode is retrieval-only. Real calls require both
`--execute-llm` and the one-process guard `V02_REAL_LLM_CONFIRMED=YES`.
The script records the provider and Base URL but never a key.

## Citation evaluation rules

For the real answers the script verified all of the following:

1. every `[n]` is within the provided source list;
2. the minimum number of distinct citations is present;
3. citations point to the expected file locator, such as CSV row 2, PDF page 1,
   or PPTX slide 1;
4. required factual terms are present;
5. injection payload strings are absent;
6. no-answer scenarios return exactly `未在文档中找到相关依据。`.

These deterministic checks supplement, but do not replace, manual review of
whether each claim is actually entailed by the cited text.

## Findings from the real LLM run

1. Retrieval, persistence, reload, metadata propagation, and score ordering
   work with the real BGE model.
2. A similarity threshold is not a factual sufficiency check. Scenarios C and D
   retrieved semantically related but insufficient text, and the real model still
   returned the exact no-evidence fallback without fabrication.
3. With `top_k=5` on this small corpus, unrelated fragments and the injection
   sample can enter contexts for other questions. The current untrusted-input
   prompt defense is therefore exercised by realistic retrieval behavior.
4. The model ignored the malicious instruction in scenario E, returned only the
   requested record ID, and cited the correct slide.
5. All generated citations were in range and mapped to the expected CSV row, PDF
   page, or PPTX slide. The service still does not enforce this at runtime; the
   validation harness checked it after generation.
6. The validation contexts are far below the 8,000-character cap, so no evidence
   about truncation behavior has yet been produced.
7. This one controlled run validates current account authorization and response
   behavior, but it is not a guarantee against future model/provider variability.

## Unresolved limitations

- Real DashScope behavior remains untested; the OpenLux result cannot be presented
  as DashScope validation.
- Only one real OpenLux run was authorized. Reproducibility across time, provider
  routes, or model revisions has not been measured.
- Exact charged cost was not available from the response/report and is not claimed.
- The threshold is corpus-dependent and allows semantically related but
  insufficient content.
- Citation correctness is evaluated by the validation harness, not enforced by
  the production service.
- Prompt-only defenses cannot fully eliminate indirect prompt injection.
- The service remains single-turn and has no reranker, hybrid retrieval, OCR, or
  structured output contract.

## Later LangChain integration guidance

This LlamaIndex baseline now passes the scoped real LLM validation. A future
LangChain comparison branch should keep the document metadata contract and
the A–F corpus unchanged, then compare an optional LangChain retriever/chain
behind the existing service boundary. Do not replace the working LlamaIndex
pipeline in-place. Keep paid integration tests opt-in and excluded from CI, and
compare retrieval sources, refusal behavior, citations, latency, and dependency
cost before choosing either implementation.
