## Architecture

The V0.2/V0.3 pipeline remains unchanged:

```text
document loaders → cleaning → SentenceSplitter → LlamaIndex index
                 → RAGService.retrieve() → traceable SearchResult
```

The new path is additive:

```text
question
  → model node (SystemMessage + conversation)
  → AIMessage.tool_calls?
      no  → final validation → direct answer
      yes → controlled tool node
              → existing search_knowledge_base StructuredTool
              → existing RAGService.retrieve()
              → structured ToolMessage with the same tool_call_id
              → model node → cited final answer
```

`LLMClient.complete()`, both V0.2 provider adapters, the V0.3 LCEL chain, and
the CLI are not modified. The Agent uses a separate ChatModel factory because
plain text completion cannot represent `AIMessage.tool_calls` or `ToolMessage`.

## ChatModel factory

`create_agent_chat_model()` supports only `LLM_PROVIDER=openai_compatible` in
V0.4.0. It explicitly passes the configured API key, Base URL, model, timeout,
and zero retries to `ChatOpenAI`. It forces Chat Completions mode and does not
send a request during construction.

DashScope remains available through the existing `LLMClient.complete()` path.
Selecting it for the Agent raises a safe capability error instead of simulating
Tool Calling.

## Tool binding and state graph

The graph binds exactly one existing `StructuredTool`:

```text
search_knowledge_base(query: string)
```

Binding uses `tool_choice="auto"` so the model decides whether retrieval is
needed and `parallel_tool_calls=False`. The tool schema, fixed `top_k`, fixed
similarity threshold, metadata allowlist, and exception sanitization are reused
from V0.3.

Graph state contains:

- the complete Human/AI/Tool message sequence;
- deduplicated, program-numbered sources;
- the number of executed knowledge-base calls;
- terminal safety status and final output.

Only a structured `AIMessage.tool_calls` entry can enter the tool node. Keywords
in user text never trigger retrieval by application code.

## Safety behavior

| Condition | Deterministic behavior |
|---|---|
| no tool call | allow a normal direct answer with no sources |
| retrieval returns no evidence | fixed `未在文档中找到相关依据。`; no extra model call |
| retrieval/tool exception | sanitized error; provider/internal detail omitted |
| invalid tool arguments | rejected by the existing Pydantic Tool schema |
| unknown tool | blocked without execution |
| multiple tool calls in one message | all blocked; parallel execution never occurs |
| third knowledge-base request | return a matching ToolMessage and terminate safely |
| model/provider exception | sanitized model error |
| unexpected non-AI model message | reject as invalid response |
| nonexistent citation | block the answer and return no sources |
| evidence answer without citation | block the answer |
| oversized source text | truncate each source to 8,000 characters before model use |

The graph has both a two-call application limit and a LangGraph recursion limit.
There is no unbounded model/tool loop.

Agent invocation explicitly runs inside a disabled LangSmith tracing context.
This prevents an ambient `LANGSMITH_TRACING=true` setting from copying user or
document content to a tracing service. API keys are excluded from `AppConfig`
representations, and provider exceptions are converted to fixed application
errors without internal details.

## Source contract

Tool results retain V0.3's `KnowledgeSource` contract. Across repeated searches,
sources are deduplicated by `source_id`, chunk index, and format locator. New
items receive monotonically increasing global source numbers. The numbers are
rewritten into each ToolMessage before the model sees them.

The final source list is produced from graph state, never parsed from model
text. Every numeric citation in a final answer must exist in that list. Direct
answers cannot invent a source number.

This is reference-integrity validation, not semantic entailment validation. A
model can still attach a real source number to a claim that contradicts the
source. A characterization test deliberately exposes this limitation so it is
not accidentally described as completed factual-grounding verification.

## Prompt-injection boundary

The fixed Agent policy is a System Message. User input remains a Human Message,
and retrieved document content remains JSON inside a ToolMessage. Documents are
explicitly described as untrusted data. They are never concatenated into or
promoted to the System Message.

This reduces direct and indirect instruction confusion but is not a complete
semantic defense against every adversarial document. Sensitive documents should
still be excluded or redacted before indexing.

## Offline tests

The scripted model double implements `bind_tools()` and emits actual LangChain
`AIMessage.tool_calls` structures. Tests inspect the second model invocation to
verify that the graph returned a `ToolMessage` with the original `tool_call_id`.
They also execute multi-turn graph paths rather than calling the tool directly.

Separate HTTP protocol tests use `httpx.MockTransport` with the real
`ChatOpenAI` serializer and response parser. They verify the outgoing Tool
Schema, `tool_choice="auto"`, `parallel_tool_calls=false`, parsed
`AIMessage.tool_calls`, serialized ToolMessage linkage, and sanitized HTTP
failures. The transport is in memory and cannot reach OpenLux or another host.

Coverage includes direct answers, retrieval, Tool Schema, query arguments,
ToolMessage linkage, no evidence, retrieval exceptions, invalid arguments,
unknown and parallel tools, loop limits, global source numbering/deduplication,
fabricated or missing citations, Prompt Injection placement, mixed content plus
tool calls, empty tool-call lists, model exceptions, unexpected ToolMessages,
unsupported providers, empty/missing tool-call IDs, unsupported content blocks,
oversized tool data, disabled tracing, and the explicit semantic-grounding
limitation.

Acceptance runs set `PYTHON_DOTENV_DISABLED=1`, blank provider credentials, and
disable LangSmith tracing. No test reads `.env`, downloads an Embedding model,
or contacts an LLM service.

## Real OpenLux validation

On 2026-11-02, the configured `gemini-3.1-flash-lite` route was validated
through `https://api.openlux.ai/v1` after a non-generating model-list check.
The run used a locally cached `BAAI/bge-small-zh-v1.5` model and a wholly
fictional TXT document. LangSmith tracing was disabled, SDK retries were zero,
and no private document or DashScope endpoint was used.

| Scenario | Model requests | Result |
|---|---:|---|
| document version retrieval | 2 | PASS: native tool call, linked ToolMessage, `V9.2 [1]` |
| general greeting | 1 | PASS: direct answer, no tool or source |
| missing administrator fact | 1 | PASS: tool call, local no-evidence refusal, no second call |

The four generation requests used 1,333 input and 100 output tokens. At the
public OpenLux price snapshot of USD 0.0184/1M input tokens and USD 0.1103/1M
output tokens, the estimated cost was USD 0.0000355572. This is an estimate;
the account invoice remains authoritative. The ignored, sanitized local report
is stored below `.validation/v0.4-real-agent-20261102/` and is not intended for
Git.

## Known limitations

- The Agent Python API is not exposed as a CLI command in V0.4.0; existing CLI
  behavior remains unchanged.
- The current Agent is synchronous and single-session; it has no persisted chat
  memory, streaming, Agent server, or multi-agent workflow.
- Only the OpenAI-compatible provider has a ChatModel factory. DashScope Agent
  support would require a separate, genuinely tool-capable ChatModel adapter.
- The model can still incorrectly skip retrieval for a document question and
  produce a direct answer; absence of a tool call is not proof of grounding.
- Citation-number validation does not prove that every generated claim is
  semantically entailed by its cited chunk.
- Prompt Injection placement is covered offline, but adversarial behavior of
  the real Agent model has not been validated with a paid attack scenario.
- The real result validates the configured account, gateway route, model, and
  three bounded synthetic scenarios; it is not a guarantee for every model or
  adversarial document.
